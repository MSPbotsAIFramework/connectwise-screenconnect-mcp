## Product design

### Goals / Non-goals

**Goals:**
- Add one new MCP tool, `screenconnect_invoke_command`, to the `connectwise-screenconnect-mcp` connector: given a session, a session group, and a PowerShell command, run the command on that session's remote machine and return its standard output text, reading from ConnectWise ScreenConnect's documented RESTful API Manager extension (`SendCommandToSession` + polling `GetSessionDetailsBySessionID`).
- Scaffold the minimum connector infrastructure this tool needs (server entrypoint, header-based credential middleware, HTTP client wrapper) if `dev/PRD-21570`'s scaffold has not been merged into `main` by the time this ticket is developed; reuse it instead if it has (dev-leg decision, see Risks & dependencies).

**Non-goals:**
- The read-only tool `screenconnect_get_live_data` — that is sibling ticket PRD-21570's scope.
- Reproducing the legacy `PageService.ashx/AddSessionEvents` + `GetSessionDetails` endpoints byte-for-byte. The tool's user-facing contract (run a command, get its output back) is preserved; the transport is the documented extension, not the undocumented legacy endpoints.
- Any command-content policy (allow-lists, blocking specific PowerShell verbs, etc.) — the tool is a transport for whatever script text the caller supplies, same trust boundary as every other "run a command on a managed endpoint" MSPbots tool; this is a platform-level RBAC/policy concern, not this connector's.
- Session types other than "Access" (same reasoning as PRD-21570: the only cited use case is a remote-PowerShell-execution workflow, which ScreenConnect only permits on Access sessions).
- Any new credential storage, OAuth flow, or admin UI. Credentials are read per-request from headers, same convention as every other MSPbots connector and as sibling ticket PRD-21570.

### Acceptance criteria AC1..AC7

- **AC1**: Given valid credential headers, a `session_id` that belongs to the named `session_group`, and a PowerShell `script`, when `screenconnect_invoke_command` is called and the remote machine reports output within `timeout` seconds, then the tool returns the command's standard output text.
- **AC2**: Given a `session_id` that exists but does not belong to the named `session_group`, when the tool is called, then it returns a structured error identifying the mismatch, and no command is sent to the session — this check exists because the tool executes arbitrary commands on a remote machine, and `session_group` is the caller-supplied safety check against sending a command to the wrong machine.
- **AC3**: Given the request is missing the instance-URL header or the auth-secret header (or both), when the tool is called, then it returns a structured 401 error naming exactly which header(s) are missing, and no HTTP request is made to the ScreenConnect instance.
- **AC4**: Given the ScreenConnect instance rejects the auth secret (upstream 401/403), or the RESTful API Manager extension is not installed/enabled on that instance (upstream 404), when the tool is called, then it returns a structured error distinguishing "authentication rejected" from "extension not reachable," and the secret value never appears in the error text or in any log line.
- **AC5**: Given the command is sent successfully but no `RanCommand` output event is observed within `timeout` seconds of polling, when the tool is called, then it returns a structured timeout error (distinct from "command failed") — the command may still complete later on the remote machine; the tool only reports that it stopped waiting.
- **AC6**: Given two tenants call the tool concurrently with different instance-URL/secret header pairs, when both requests are in flight at the same time, then each request's upstream calls (`SendCommandToSession` and its polling `GetSessionDetailsBySessionID` calls) use only the credentials and session id supplied on that same request — no credential, session, or output data crosses between the two.
- **AC7**: Given a `session_id` that does not exist at all on the instance, when the tool is called, then it returns a structured "session not found" error (from the `session_group` membership check in AC2, which also covers non-existent sessions), and no command is sent.

## Tech design

### Conclusion

Build `screenconnect_invoke_command` by calling ConnectWise ScreenConnect's documented RESTful API Manager extension: `SendCommandToSession` to queue the PowerShell command, then poll `GetSessionDetailsBySessionID` until a correlated `RanCommand` event (or `timeout`) is observed — not the undocumented legacy `PageService.ashx/AddSessionEvents` + `GetSessionDetails` flow Rewst's action currently uses. This keeps the connector on a vendor-maintained, documented contract and mirrors the precedent already set on this ticket's own prior `[BLOCKED]` investigation and on sibling ticket PRD-21570.

Nowhere on `main` (`README.md:1-2` only, commit `410e37a`). ### Data & API contract

**Credential headers** (reused from PRD-21570's design for this same repo, not re-invented):

| Header | Required | Meaning |
|---|---|---|
| `X-ScreenConnect-Instance-Url` | Yes | Base URL of the customer's ScreenConnect instance |
| `X-ScreenConnect-Auth-Secret` | Yes | Value configured as `RESTfulAuthenticationSecret` on that instance's RESTful API Manager extension; sent upstream as `CTRLAuthHeader` |
| `X-ScreenConnect-Origin` | No | Only needed if the instance's extension has `RESTfulAllowedOrigin` configured; when absent, no `Origin` header is sent upstream |

**Tool**: `screenconnect_invoke_command`

- Input:
  - `session_id` (string, required) — the target session's id.
  - `session_group` (string, required) — the group/folder name the session is expected to belong to; used as a safety check (AC2/AC7), not just a label.
  - `script` (string, required) — PowerShell command text to run on the session's remote machine.
  - `timeout` (integer, optional, default TBD at implementation, e.g. 60 seconds) — how long to poll for output before returning the AC5 timeout error.
- Output: the command's standard output text (string), on success.

**Upstream HTTP calls**:

```
1) Resolve + validate session:
   POST {instance_url}/App_Extensions/2d558935-686a-4bd0-9991-07539f5fe749/Service.ashx/GetSessionBySessionID
   Body: ["<session_id>"]
   -> if not found: AC7 error. If found but its group does not match session_group: AC2 error.

2) Queue the command:
   POST {instance_url}/App_Extensions/2d558935-686a-4bd0-9991-07539f5fe749/Service.ashx/SendCommandToSession
   Content-Type: application/json
   CTRLAuthHeader: <secret>
   [Origin: <value>]                      -- only if X-ScreenConnect-Origin was supplied
   Body: ["<session_id>", "<script>"]

3) Poll for output (bounded by `timeout`):
   POST {instance_url}/App_Extensions/2d558935-686a-4bd0-9991-07539f5fe749/Service.ashx/GetSessionDetailsBySessionID
   Body: ["<session_id>"]
   -> inspect the session's events for a RanCommand event correlated to step 2's request
      (exact correlation and field extraction confirmed at implementation time, see Open questions)
   -> on match: return its output text (AC1)
   -> on no match before `timeout` elapses: AC5 timeout error
```

**Error mapping**:

| Condition | Tool response |
|---|---|
| Required header(s) missing | 401, body lists the missing header name(s); no upstream call made (AC3) |
| `session_id` not found | Structured "session not found" error; no command sent (AC7) |
| `session_id` found but not in `session_group` | Structured "session not in expected group" error; no command sent (AC2) |
| Upstream 401/403 on any call | Structured error: "ScreenConnect rejected the auth secret for this instance" (secret never included) (AC4) |
| Upstream 404 on the extension path | Structured error: "RESTful API Manager extension not installed or not enabled on this ScreenConnect instance" (AC4) |
| `RanCommand` not observed within `timeout` | Structured timeout error, distinct from a failure (AC5) |
| Upstream timeout / connection failure | Structured error: "ScreenConnect instance unreachable" (includes the instance host, not the secret) |

**Backward compatibility**: first version of this tool in a brand-new connector — no existing tenants or consumers, so there is no compatibility constraint beyond keeping this contract stable so sibling ticket PRD-21570's tool continues to work unmodified once both are in the same repo (see 1.2 cross-repo-independence rule — not applicable here since both land in the same repo, but the same spirit of not breaking the sibling's tool applies at merge time).

### Key flow / sequence

```
Agent -> Gateway -> connectwise-screenconnect-mcp
                       (middleware reads 2-3 headers into per-request context)
                       -> POST .../GetSessionBySessionID            (validate session_id + session_group)
                       -> POST .../SendCommandToSession              (queue the PowerShell command)
                       -> poll POST .../GetSessionDetailsBySessionID (until RanCommand event or timeout)
                       (map response / error) -> tool output (stdout text, or structured error)
```

### Non-functional

- **Idempotency / concurrency**: `screenconnect_invoke_command` is **not** idempotent — it runs a command on a remote machine; retrying it re-runs the command. Concurrent requests from different tenants are isolated purely by per-request header + session-id context — no shared state, no credential caching (SOP's three iron rules: headers only, per-request isolation, truly stateless) (AC6).
- **Performance**: one upstream call to validate, one to queue, and a bounded number of polling calls (frequency and backoff confirmed at implementation time) until `RanCommand` appears or `timeout` elapses. `timeout` bounds worst-case latency; the tool must not poll forever.
- **Security**: the secret is transmitted via header only, never logged, never persisted to disk or environment; never appears in tool output, error text, or log lines (AC4). The `script` text itself (arbitrary PowerShell) is not filtered or sanitized by this connector — it is a transport, same trust boundary as the platform's other remote-execution tools; this is called out explicitly in Non-goals and Reuse & cleanup's follow-ups.
- **Multi-tenant isolation**: enforced entirely by requiring the caller (Gateway) to supply per-tenant instance URL + secret on every call; the connector holds no tenant state between requests (AC6). The `session_group` check (AC2) adds a second, intra-tenant safety boundary: even within one tenant's ScreenConnect instance, a caller cannot run a command on a session outside the group it named.
- **Observability**: log tool name, the instance host (not the full URL — no embedded credential), the target `session_id` and `session_group`, the upstream HTTP statuses for all three calls, poll count, and total latency; never log header values or the `script` text's content (script content may itself be sensitive).

- **Arbitrary remote command execution**: this tool is a generic remote-PowerShell-execution primitive, gated only by the platform's existing per-tenant header-credential model and the AC2 session/group check — no command-content policy exists at this layer (see Non-goals).
