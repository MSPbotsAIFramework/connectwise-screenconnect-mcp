One line: Add a ConnectWise ScreenConnect MCP tool, screenconnect_get_live_data, that returns the live session list for a session group, so the Rewst flow "CW Control: Run Powershell" (Ginko IT) can be migrated off Rewst without losing session lookup.

## Product design

### Goals / Non-goals

**Goals:**
- Add one new MCP tool, `screenconnect_get_live_data`, to the (currently empty) `connectwise-screenconnect-mcp` connector: given a session type and a session group name, return the live session list for that group, reading from ConnectWise ScreenConnect's documented RESTful API Manager extension.
- Scaffold the minimum connector infrastructure needed to ship that one tool (server entrypoint, header-based credential middleware, HTTP client wrapper), per the vendor-mcp-development SOP.

**Non-goals:**
- The write/control tool `screenconnect_invoke_command` — that is sibling ticket PRD-21572's scope, not this ticket's. This design only scaffolds what `screenconnect_get_live_data` itself needs; it deliberately does not try to anticipate PRD-21572's tool shape beyond keeping the client module easy to extend (see Tech design §4a).
- Reproducing the legacy `PageService.ashx/GetLiveData` endpoint byte-for-byte. The tool's user-facing contract (read a group's live sessions) is preserved; the transport is intentionally the documented extension, not the undocumented legacy endpoint.
- Session types other than "Access" (see Open questions) — out of scope for v1; the ticket's only cited use case (Rewst's `CW Control: Run Powershell`) is an Access-session workflow.
- Any new credential storage, OAuth flow, or admin UI. Credentials are read per-request from headers, same as every other MSPbots connector.

### Acceptance criteria AC1..AC6

- **AC1**: Given a valid ScreenConnect instance URL and a valid RESTful API Manager auth secret are supplied via headers, and the named session group has one or more live sessions, when `screenconnect_get_live_data` is called with that session type and group name, then the tool returns the list of live sessions in that group (at minimum: session id, display name, group path, connected state), sourced from the extension's `GetSessionsByFilter` method.
- **AC2**: Given the named session group exists but currently has zero live sessions, when the tool is called, then it returns an empty list, not an error.
- **AC3**: Given the request is missing the instance URL header or the auth secret header (or both), when the tool is called, then it returns a structured 401 error that names exactly which header(s) are missing, and no HTTP request is made to the ScreenConnect instance.
- **AC4**: Given the ScreenConnect instance rejects the auth secret (upstream 401/403), or the RESTful API Manager extension is not installed/enabled on that instance (upstream 404), when the tool is called, then it returns a structured error that distinguishes "authentication rejected" from "extension not reachable," and the secret value never appears in the error text or in any log line.
- **AC5**: Given two tenants call the tool concurrently with different instance-URL/secret header pairs, when both requests are in flight at the same time, then each request's upstream call uses only the credentials supplied on that same request — no credential or response data crosses between the two.
- **AC6**: Given a session group name that does not exist at all on the instance, when the tool is called, then it returns an empty list (ScreenConnect's filter simply matches nothing) rather than a distinguishable "group not found" error — this is a documented non-goal, not a defect, because the vendor API has no "does this group exist" check to call first.

### Open questions

- [Assumed, non-blocking] `GetSessionsByFilter`'s filter-string grammar for combining a session type and a group name is not shown on the scraped public reference page (it documents the method signature and return category, not a full query-language spec). Assumption: implement by building a filter string from ScreenConnect's standard session-search syntax (the same syntax used in the host client's session search box), confirmed against a live or sandbox instance at implementation time; if that syntax does not support group-name filtering cleanly, fall back to `GetSessionsByName` scoped by name prefix. If this assumption is wrong, only Tech design §5 (the exact HTTP body construction) needs revision — the tool's input/output contract (AC1-AC6) does not change.
- [Assumed, non-blocking] The ticket's example `session_type: 2` is assumed to mean ScreenConnect's "Access" session type (as opposed to "Support" or "Meeting"), based on the cited Rewst flow being a remote-PowerShell-execution use case, which ScreenConnect only permits on Access sessions. Dev confirms the exact enum ordinal against the extension's `CreateSession(SessionType sessionType, ...)` signature or a live instance before implementation. v1 ships with `session_type` scoped to `"Access"` only (see Non-goals); if the assumption is wrong the enum label changes, not the tool shape.

## Tech design

### Conclusion

Build `screenconnect_get_live_data` as the first tool in a from-scratch MCP server scaffold (the repo currently has only a README), calling ConnectWise ScreenConnect's documented RESTful API Manager extension method `GetSessionsByFilter` over HTTP, authenticated with a per-request `CTRLAuthHeader` sourced from an MSPbots connector header — not the undocumented legacy `PageService.ashx/GetLiveData` endpoint Rewst's flow currently calls. This keeps the connector on a vendor-maintained, documented contract, consistent with the precedent already set on sibling ticket PRD-21571.

### Where the current implementation lives

Nowhere yet. `README.md:1-2` is the entire repository content at `410e37a`. This is a first-version build (vendor-mcp-development SOP "main line A"), not a modification.

### Data & API contract

**Credential headers** (new — first version of this connector):

| Header | Required | Meaning |
|---|---|---|
| `X-ScreenConnect-Instance-Url` | Yes | Base URL of the customer's ScreenConnect instance, e.g. `https://control.screenconnect.com` or a self-hosted `https://<tenant>.screenconnect.com` |
| `X-ScreenConnect-Auth-Secret` | Yes | Value configured as `RESTfulAuthenticationSecret` on that instance's RESTful API Manager extension; sent upstream as the `CTRLAuthHeader` header |
| `X-ScreenConnect-Origin` | No | Only needed if the instance's extension has `RESTfulAllowedOrigin` configured; when this header is absent, the connector sends no `Origin` header upstream |

**Tool**: `screenconnect_get_live_data`

- Input:
  - `session_type` (string enum, v1 only accepts `"Access"`) — see Open questions for the enum-mapping assumption.
  - `session_group` (string, required) — the group/folder name as shown in the ScreenConnect session list, e.g. `"All Machines"`.
- Output: list of objects — `session_id`, `name`, `group_path`, `is_connected`, `guest_info` — field names taken from the vendor docs' "List of sessions" return category; exact JSON field names confirmed against a live call at implementation time, since the public reference documents method signatures and return categories, not a full JSON schema.

**Upstream HTTP call**:

```
POST {instance_url}/App_Extensions/2d558935-686a-4bd0-9991-07539f5fe749/Service.ashx/GetSessionsByFilter
Content-Type: application/json
CTRLAuthHeader: <secret>
[Origin: <value>]                      -- only if X-ScreenConnect-Origin was supplied
Body: ["<filter string built from session_type + session_group>"]
```

**Error mapping**:

| Condition | Tool response |
|---|---|
| Required header(s) missing | 401, body lists the missing header name(s); no upstream call made |
| Upstream 401/403 | Structured error: "ScreenConnect rejected the auth secret for this instance" (secret never included) |
| Upstream 404 on the extension path | Structured error: "RESTful API Manager extension not installed or not enabled on this ScreenConnect instance" |
| Upstream timeout / connection failure | Structured error: "ScreenConnect instance unreachable" (includes the instance host for diagnosis, not the secret) |
| Filter matches no sessions | Empty list (AC2/AC6), not an error |

**Backward compatibility**: first version of a brand-new MCP — no existing tenants or consumers yet, so there is no compatibility constraint beyond matching this contract exactly so sibling ticket PRD-21572 can build its tool alongside it.

### Key flow / sequence

```
Agent -> Gateway -> connectwise-screenconnect-mcp
                       (middleware reads 2-3 headers into per-request context)
                       -> POST {instance}/App_Extensions/.../GetSessionsByFilter
                          (CTRLAuthHeader: <secret>)
                       <- ScreenConnect instance (RESTful API Manager extension)
                       (map response / error) -> tool output
```

### Non-functional

- **Idempotency / concurrency**: the tool is read-only; concurrent requests from different tenants are isolated purely by per-request header context — no shared state, no credential caching (SOP's three iron rules: headers only, per-request isolation, truly stateless).
- **Performance**: one upstream HTTP call per tool invocation. `GetSessionsByFilter` is not documented as paginated, so the result set size is whatever ScreenConnect returns for that group; no explicit page/limit handling is in scope for v1.
- **Security**: the secret is transmitted via header only, never logged, never persisted to disk or environment; `CTRLAuthHeader`'s value never appears in tool output, error text, or log lines (AC4).
- **Multi-tenant isolation**: enforced entirely by requiring the caller (Gateway) to supply per-tenant instance URL + secret on every call; the connector holds no tenant state between requests (AC5).
- **Observability**: log tool name, the instance host (not full URL — there is no embedded credential in the URL itself, but no query-string leakage either), the upstream HTTP status, and latency; never log header values.
