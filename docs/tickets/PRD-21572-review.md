### Findings

1. [must-fix] `src/connectwise_screenconnect_mcp/tools/commands.py:48-50` — The tool's `timeout` parameter accepts up to `le=600` (10 minutes), but `src/connectwise_screenconnect_mcp/api_client.py:39` documents, in this same repo, that "the gateway times a tool call out at 120s" (`_CALL_BUDGET_SECONDS = 100.0`) — and the vendor-mcp-development SOP states this as a hard requirement, not a guideline: "单次工具调用总耗时（含重试）必须 < 120s，超出会被上游判超时" (SOP §5), repeated as a §14 delivery-checklist item. `invoke_command` (`commands.py:72-120`) first calls `get_session_by_id` (`api_client.py:237`, a retried/idempotent call that can itself take up to `_CALL_BUDGET_SECONDS=100s` under retry/backoff), then `send_command_to_session` (`api_client.py:256`), then polls `get_session_details` in a loop bounded by the caller-supplied `timeout` (`commands.py:106-119`) — so for any `timeout` value above roughly 100-110s (well within the field's allowed `1..600` range; the default is only 60s, so a caller legitimately waiting longer for a slow remote command will reach it), the MCP gateway will kill the whole tool call at 120s before this tool's own polling loop reaches its deadline. The result: AC5's contract ("it returns a structured timeout error, distinct from a failure") silently cannot be honored for any caller-supplied `timeout` above that threshold — the caller gets whatever generic/unstructured error the gateway itself produces instead of this connector's `408 timeout` envelope, which is exactly the behavior AC5 was written to rule out. Fix: cap `Timeout`'s `le` to a value that leaves headroom under the repo's own 120s budget together with the two setup calls — e.g. `le=90` with an explicit comment pointing at `api_client.py`'s `_CALL_BUDGET_SECONDS` / the SOP §5 limit — or otherwise account for the setup-call time against the polling deadline so the total never approaches 120s.
